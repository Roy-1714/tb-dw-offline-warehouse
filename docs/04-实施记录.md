## 1. 数据路径与用户口述不符

- 现象：口头说原始数据在 `/data/raw`、封装脚本在 `/bin`
- 实测：`/data/raw` 不存在；真实路径 `/home/atguigu/data/raw`；`/bin` 是 `/usr/bin` 软链，用户脚本在 `/home/atguigu/bin`
- 处理：以实测路径为准，全部脚本改为绝对路径
- 教训：**口头路径必须实测校正再写进脚本**

## 2. Spark 装的是 without-hadoop 版，`spark-sql` 起不来

- 现象：`Failed to load class org.apache.spark.sql.hive.thriftserver.SparkSQLCLIDriver`
- 排查：`/opt/module/spark-3.3.1/jars` 共 184 个 jar，**没有 spark-hive / hive-exec**
- 处理：从 `/opt/software/spark-3.3.1-bin-hadoop3.tgz` 解压到独立目录 `/opt/module/spark-3.3.1-hadoop3`（不动原目录），调用时显式 `export SPARK_HOME=...`
- 第二个坑：`.bashrc` 里 `SPARK_HOME` 仍指向旧目录，`spark-sql` 脚本优先读环境变量，必须覆盖
- 第三个坑：`spark-env.sh` 没设 `HADOOP_CONF_DIR`，跑 YARN 报错，改为每次执行注入
- 第四个坑：YARN 端要分发 jar，打 archive 上传 HDFS，用 `spark.yarn.archive` 指定（266 MB）

## 3. Hive Metastore 不常驻

- 现象：beeline 连 `hadoop102:10000` 被拒；`hive.metastore.uris=thrift://hadoop102:9083` 无人监听
- 处理：`hive --service metastore` 以 atguigu 身份后台启动，等 9083 监听后再跑 SQL
- 注意：重启机器后要重新拉起

## 4. 动态分区 strict 模式报错

- 现象：`Dynamic partition strict mode requires at least one static partition column`
- 处理：`SET hive.exec.dynamic.partition.mode=nonstrict` + 启动参数 `spark.hadoop.hive.exec.dynamic.partition.mode=nonstrict`
- 备注：Spark 里 `SET hive.*` 会告警"may not work"，所以必须同时用 `spark.hadoop.` 前缀从启动参数传入

## 5. **时区边界写错，118 万行被误判越界（最值得讲的一个 bug）**

- 现象：ODS 装载后总量对得上（100,150,807），但 11-25 分区只有 9,238,584 行（awk 画像为 10,420,015），`invalid` 分区却有 1,236,274 行（预期约 5.5 万）
- 排查：把"总量对齐"当唯一验收标准会掩盖问题；改成**逐分区对齐**
- 根因：`ts` 是 UTC 秒。业务日 2017-11-25 00:00:00+08 对应 `1511539200`，而我写成了 `1511568000`（= 11-25 08:00+08，即 UTC 零点），于是 11-25 前 8 小时的 1,180,698 行被划进 invalid；上界同理多放了 12-04 的 733 行
- 处理：边界改为 `1511539200 ~ 1512316799`，并加 `ALTER TABLE ... DROP IF EXISTS PARTITION (dt='2017-12-04')` 清掉脏分区
- 教训：**时间戳分区必须按本地业务时区换算上下界，并与会话时区（`spark.sql.session.timeZone`）对齐；验收必须逐日比对**

## 6. 容器 exit 137 / executor 120 秒无响应

- 现象：`Container killed on request. Exit code is 137`；随后 `Cannot receive any reply from /192.168.150.103 in 120 seconds`
- 排查：`free -g` 显示 swap 已被用掉 1 G；进一步发现 **103/104 物理内存只有 3.7 G，而 YARN 每节点配额写的是 4 G**——配额本身超过物理内存
- 处理：Spark 从 driver 2g + executor 2g×3 降到 **driver 1g + executor 1g×2 + overhead 384m**，`shuffle.partitions` 40→30，`network.timeout`/`rpc.askTimeout` 放宽到 600s
- 教训：**小集群先减并发，不要加内存**；`yarn.nodemanager.resource.memory-mb` 必须小于物理内存

## 7. 整机失联（物理机磁盘被打满）

- 现象：三台 VM 的 22/12345/9083 全部不可达
- 根因：宿主机磁盘被写满（HDFS 多副本 + ORC 中间文件 + 日志）
- 处理：用户清理宿主机磁盘后重启 VM；重启后 HDFS 自动恢复，`safemode` 为 OFF
- 教训：**动手前先看宿主机与 VM 的容量水位**；HDFS 3 副本意味着 1 GB 原始数据占 3 GB

## 8. DolphinScheduler 2.0.5 的坑

- **版本不是 3.x**：`lib` 下 `dolphinscheduler-common-2.0.5.jar`，但 `bin/env` 里同时存在 3.x 风格的 `application-master.yaml`
- **API 用表单参数**：项目创建用 JSON body 报 `MissingServletRequestParameterException: 'projectName'`，改成 `application/x-www-form-urlencoded` 后才成功
- **默认堆过大**：`bin/dolphinscheduler-daemon.sh` 里 master 是 `-Xms4g -Xmx4g`、worker 是 `-Xms2g -Xmx2g`，在 3.7 G 的机器上直接被 OOM 干掉（日志无异常、进程消失）。已备份原脚本并改为 1g/1g
- **master 起不来的第二个原因**：ZK 选主尚未完成时启动会报 `zookeeper connect timeout`，等 ZK 稳定后重启即可
- **stop-all 卡住**：脚本内部 `ssh` 到 103/104 时弹 `密码：` 提示并挂起；用 `dolphinscheduler-daemon.sh stop <service>` 逐个停更可靠
- **服务分布**：master/api/alert 在 102，worker/logger 分布在 103/104

## 9. Spark 的两个语法/路径限制（写 SQL 时必踩）

- **`count(distinct) over(...)` 不支持**：
  商品维需要"每个商品涉及几个类目"，写成 `count(DISTINCT category_id) OVER (PARTITION BY item_id)` 直接报
  `Distinct window functions are not supported`。
  改法：拆成「商品×类目计数 + 窗口排名」与「商品级汇总」两次聚合，再按 `item_id` join。

- **同一张表不能既读又写**：
  用户累计快照原本设计为「读前一日的 `dws_user_action_td` 分区 + 当日 1d 增量 → 覆盖写入当日分区」，
  Spark 报 `Cannot overwrite a path that is also being read from`。
  改法：`dws_user_action_td` 改为从 `dws_user_action_1d` 汇总截止当日重算
  （1d 表每天约 100 万行，重算成本远低于维护中间表规避路径冲突）。

- **分区表建表时漏 `PARTITIONED BY`**：
  `dwd_dq_stat` 第一次建表把 `dt` 写成普通列，插入时用 `PARTITION (dt=...)` 报
  `dt is not a valid partition column`。已改为真正的分区表。

## 10. 最严重的一个设计错误：按天脚本里的 `DROP TABLE` 把历史分区删光了

- 现象：9 天回填全部 `rc=0`，但验收 SQL 查出 **DWD 只有 2017-12-03 一天的数据**；HDFS 里 9 个分区目录都在（看起来正常），可 `count(*)` 只有一天
- 排查：`SHOW PARTITIONS` 与 `count(*)` 对比才暴露；此前只看 HDFS 目录数量，得到的是**假象**
- 根因：每个按天执行的 SQL 文件开头都写了 `DROP TABLE IF EXISTS <表>; CREATE TABLE <表> ...`。按天循环时，第二天开头就把前一天的表连数据一起 DROP 掉了（`LOCATION` 指向的目录被清空，仅留下空的分区目录结构）。表现就是"每天成功、结果只剩最后一天"
- 修复：DDL 与 DML 分离
  - 按天脚本改为 `CREATE TABLE IF NOT EXISTS`，不再 DROP
  - 新增 `sql/00_reset.sql` 只在需要从零重建时使用
  - 新增 `script/00_full_rebuild.sh`：清派生层 → 9 天全链路 → 导出
- 教训：**幂等不是"重复执行不报错"，而是"重复执行不破坏已有数据"**；验收必须查行数，不能只查目录/分区数

## 11. DolphinScheduler API 的正确用法（2.0.5）

单机 standalone 启动后，接口路径与常见文档不一致，靠 `/v2/api-docs`（swagger）才定位准确：

| 动作 | 接口 | 说明 |
|---|---|---|
| 登录 | `POST /login` | 表单参数 `userName/userPassword`，返回 `sessionId`，后续靠 Cookie 复用 |
| 建项目 | `POST /projects` | **表单参数**（JSON body 会报 `MissingServletRequestParameter 'projectName'`） |
| 建流程 | `POST /projects/{code}/process-definition` | 必填参数名是 **`taskDefinitionJson`**（不是 `tasks`），配 `taskRelationJson`、`locations` |
| 上线 | `POST /projects/{code}/process-definition/{code}/release` | `releaseState=ONLINE` |
| **运行** | `POST /projects/{code}/executors/start-process-instance` | 若写成 `/executions` 会 404；必填 `failureStrategy`、`processDefinitionCode`、`processInstancePriority`、`scheduleTime`、`warningGroupId`、`warningType` |
| 查实例 | `GET /projects/{code}/process-instances` | 返回 `state`、起止时间 |

其它坑：
- 管理入口端口是 **12345**（api），`/dolphinscheduler/ui` 是前端
- standalone 模式下 master/worker/api/alert/zk 全在一个 JVM，端口 12345/5678/50052/1234 都会监听

## 12. ODS 装载的幂等标记

工作流里第一个节点是 ODS 全量装载（1 亿行，约 8~10 分钟）。日常调度若每次都重跑，既慢又占资源，因此在装载成功后写标记：

```bash
/warehouse/tb_dw/ods/ods_user_behavior/_LOADED
```

存在标记则跳过装载，删除标记即可强制重装。这样"调度重跑"与"首次装载"语义分离，也方便验收。

## 13. 远程执行的工程化处理

- Windows PowerShell 传给 `ssh.exe` 的多行命令会**被吃掉引号**、内联管道被打断
- 处理：所有远端动作一律"本地写脚本 → pscp 上传 → `ssh bash /tmp/x.sh`"，脚本内部把结果重定向到文件，本地再读文件过滤
- 换行：Windows 写出的文件是 CRLF，远端 bash 会报 `$'\r': 未找到命令`，上传后统一 `sed -i 's/\r$//'`
- 身份：Spark 必须以 `atguigu` 运行，用 root 跑会报 `Permission denied: user=root, access=WRITE, inode="/user"`
- 密码登录：`ssh`/`SSH_ASKPASS` 在非交互环境不可用，最终用 PuTTY 的 `plink`/`pscp` 做一次性密码登录并安装公钥，之后全程免密

## 14. 三个"看起来像环境问题、其实是配置问题"的坑（最后都定位到根因）

1. **调度任务 0 秒失败（`sh: hdfs: 未找到命令`）**
   DS 用 `sudo -u atguigu sh cmd` 执行，**不加载 .bashrc**，实测 PATH 只有 `/sbin:/bin:/usr/sbin:/usr/bin`，
   `hdfs`、`spark-sql`、`java` 全都找不到。修法：把 `JAVA_HOME/HADOOP_HOME/HIVE_HOME/SPARK_HOME` 与
   `PATH` 全部显式写进 `script/00_env.sh`，脚本不再依赖外部 shell 环境。

2. **`00_env.sh: 行1: ﻿#!/bin/bash: 权限不够`**
   用 PowerShell 改文件时写入了 UTF-8 BOM，bash source 时把 BOM 当成命令的一部分。
   修法：文件一律用编辑器/脚本写入并去 BOM，部署后再 `bash -n` 校验语法。

3. **driver 被系统杀掉（`已杀死 spark-sql`）**
   ADS 节点扫描 1366 万行时，1 G 的 driver 堆被 OOM Killer 直接 SIGKILL，DS 侧表现为任务 KILL。
   修法：driver 提到 1.5 G（DS standalone 只占约 1.5 G，内存够），executor 维持 1 G × 2。

## 15. 自动补数的教训

DS 2.0.5 的 `startNodeList` 参数传任务名会报
`start node name [08_ads_core_1d] is not in task node list`，`processDag is null`，实例卡在 RUNNING 但无任务。
结论：**别用 startNodeList 补数**，改为整条重跑（前几个节点有标记会秒过），或用 DS 前端的"从失败节点恢复"。
