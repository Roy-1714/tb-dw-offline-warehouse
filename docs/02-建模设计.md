# 02 建模设计

## 1. 为什么不能照搬"业务库多表"的数仓模型

常见电商数仓（如 gmall）是「业务库 30 张表 → ODS 全量/增量同步 → 维度建模」。
本项目的数据源只有**一张宽事件表**（user_id, item_id, category_id, behavior, ts），没有独立的用户表、商品表、订单表、支付表。

所以本项目的建模选择是：

- **ODS**：一张按天分区的行为明细表，原样保留字段
- **DIM**：维度只能"从事实反推"——日期维静态生成；商品维从行为聚合出主类目与跨类目标记
- **DWD**：清洗、去重、派生时间字段后的行为明细（唯一事实表）
- **DWS**：按用户/商品/类目三个粒度做日汇总，再加滚动与累计快照
- **ADS**：10 张面向分析的指标表

这是「单一事实表 + 退化维度」的建模路径，与"多业务表星型模型"的差别要在面试/文档里讲清楚，不能假装自己有独立维表。

## 3. 存储与压缩

| 层 | 格式 | 理由 |
|---|---|---|
| ODS | TextFile，不压缩 | 保留原始可回溯；`load`/审查直接用；可切分，不因压缩变单分区 |
| DWD/DWS/ADS | ORC + snappy | 列存 + 压缩，后续按列扫描；snappy 保证可切分且 CPU 开销低 |

## 4. 分区策略

- 分区键统一 `dt`（`yyyy-MM-dd`，**北京时**）
- 分区由事件时间 `ts` 派生，**不依赖文件行序**（实测 98.8 万行乱序）
- 边界换算：`ts` 是 UTC 秒，业务日按 UTC+8 切分

  ```
  2017-11-25 00:00:00 +08 = 1511539200
  2017-12-03 23:59:59 +08 = 1512316799
  ```

  （**踩过的坑**：最初误用 1511568000/1512345599，等于把边界当成 UTC 零点，导致 11-25 前 8 小时共 118 万行被错判越界、12-04 多出 733 行。详见 04-实施记录。）

- 越界数据进 `dt='invalid'`，不丢、不混入正常分区
- ADS 表除业务列 `dt` 外另设分区列 `dt_part`，避免"分区列与数据列重名"导致的歧义

## 5. 增量与重算策略

| 场景 | 策略 |
|---|---|
| DWD | 按天增量，`INSERT OVERWRITE ... PARTITION(dt=业务日)` |
| DWS 1d | 按天增量 |
| DWS nd（滚动 7 日） | 每次从 1d 汇总重算 7 天，不扫明细 |
| DWS td（累计） | 从 `dws_user_action_1d` 汇总截止当日重算（1d 表每日约 100 万行，量小；且规避了"读写同一张表"的路径冲突，见 04-实施记录） |
| DIM dim_item | 全量重算（商品属性会随历史变化，且仅 416 万行，一次性任务） |
| ADS | 按天增量 |
| 回溯 | `00_backfill.sh` 按日期顺序循环调用各节点脚本，td 依赖前一日快照，故**必须顺序执行** |

## 6. 调度 DAG（10 节点串行）

```
01_ods_load
  → 02_dim_date_init
  → 03_dwd_detail_1d
  → 04_dim_item
  → 05_dws_user_1d
  → 06_dws_item_category_1d
  → 07_dws_nd_td
  → 08_ads_core_1d
  → 09_ads_topic_1d
  → 10_export_mysql
```

- 参数 `do_date` 由调度传入，脚本把 SQL 里的 `@DO_DATE@` 渲染成具体日期
- 07 节点依赖前一日 `dws_user_action_td` 快照，因此 DAG 内顺序不可乱；回溯时也必须按日期升序

## 7. 计算引擎与资源

- 引擎：**Spark SQL（spark-sql CLI，client 模式，运行在 YARN）**
- 为什么不用 Hive on MR：`/opt/module/spark-3.3.1` 是 `bin-without-hadoop` 版，缺 Hive 支持；另解压 `spark-3.3.1-bin-hadoop3` 到独立目录使用，不动原目录
- 资源约束（实测）：hadoop102 内存 7.8G，**hadoop103/104 仅 3.7G**，而 YARN 每节点配额 4G
- 因此 Spark 侧固定为：driver 1g、executor 1g×2、overhead 384m、shuffle partitions 30，RPC/网络超时放宽到 600s
- 结论：**小集群里先减并发，不要加内存**
